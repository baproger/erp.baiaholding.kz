## 0. Суть проекта

**BAIA ERP** — внутренняя ERP/CRM для холдинга из двух фирм: **BAIA** (мебельное производство: металл + дерево) и **ASU** (швейный цех). Продакшн: `erp.baiaholding.kz` (Plesk). Заменяет Excel-файлы и тетради бухгалтерии.

Жизненный цикл денег и сделки:
1. **Предварительная сделка (лот)** — менеджер вносит цифры лота госзакупки, система считает маржу; ≥15% → «Подтвердить» → создаётся сделка.
2. **Сделка** идёт по воронке: Договор → Дизайн и расчет (гейт дизайнера) → Закуп ЛДСП,МДФ (уведомление снабженцу) → «В цех».
3. **Цех** (у BAIA два: Металл / Ағаш, у ASU один) — заказ идёт по этапам цеха с таймингом каждого этапа; «Готово» возвращает сделку на Логистику.
4. Логистика → Сборка → Акт → ЭСФ → **Оплата успешно** (двигает только бухгалтер).
5. **Финансы**: счета («Аванс»), платежи, расходы (по сделкам и компании), поступления, касса/банк, дебиторка/кредиторка. **ЗП**: оклад + ступенчатый бонус от маржи. **Аналитика/Сводный отчёт** — для руководства. **ТВ-экраны** в цехах и офисе — живые канбаны/рейтинги по коду доступа.

## 1. Технологии
- **Backend:** Laravel 13 (локально PHP 8.5, прод PHP 8.3 — composer.json `config.platform.php=8.3.30`), MySQL
- **Frontend:** Inertia.js + Vue 3 + Tailwind + Vite (Laravel Breeze)
- **Права:** spatie/laravel-permission (RBAC). **Admin — глобальный суперпользователь** (Gate::before, worksInCompany=true везде). Роль admin назначает только admin; последний активный админ защищён от разжалования/деактивации; админа редактирует/деактивирует только админ.
- **Таймзона:** Asia/Almaty (+05:00); **Локализация:** ru / kk
- **Тесты:** PHPUnit — 240+, все зелёные. Перед каждым push: `npm run build` + `php artisan test`.
- **Продакшн (Plesk):** сессии/кэш — файлы, очередь — sync; `public/build/` закоммичен, а `vendor/` — НЕТ (в .gitignore): его пересобирает деплой командой `php composer.phar install --no-dev` (composer.phar лежит в репозитории, см. DEPLOY.md); деплой — `DEPLOY.md` (Git Pull → composer.phar install → `php artisan migrate --force` → `php artisan optimize`). CLI PHP на сервере без pdo_mysql — миграции гнать через Laravel Toolkit или веб-скрипт под FPM.

## 2. Роли и доступы
| Роль | Что видит / может |
|------|-----------|
| **admin** (СЕО) | всё; только он удаляет сделки и назначает роль admin |
| **director** | всё как наблюдатель; этапы АКТ/ЭСФ/Оплата не двигает |
| **financist** (Финансист-Бухгалтер) | финансы, аналитика, ЗП, создание сделок, сотрудники (просмотр/добавление/правка/деактивация, кроме админов), категории расходов, план продаж |
| **manager** | ТОЛЬКО свои сделки/лоты/цех/финансы/бонус; общей аналитики не видит |
| **employee (цех)** | карточки цеха (двигает этапы), свои задачи; суммы не видит |
| **lawyer / cook** | уровень «сотрудник»: цех, задачи, своя ЗП |
| **designer / supplier** («Технолог»→«Снабженец») | как сотрудник + сделки: в списках видят ТОЛЬКО сделки своего гейт-этапа (design/shop_gate), по прямой ссылке — любую сделку компании; при входе сделки на их этап — задача+уведомление, без их галочки сделка дальше не идёт |

## 3. Модули
- **Предв. сделки (/pre-deals):** лоты как Excel отдела продаж — № лота, БИН, заказчик, товар, контакт (имя+телефон), сумма/закуп/партнёр %/доставка/комиссия; авто-расчёт (PreDeal::calculate): партнёр=%×сумма, налог=ставка×сумма, остаток=сумма−всё, маржа=остаток/сумма (живой расчёт и в форме). Маржа ≥ порога (Setting `predeal_min_margin`, 15%) — «выиграл: да» + кнопка «Выиграл ✓» → создаётся сделка и происходит редирект на страницу «Сделки» (номер, бюджет, ответственный=менеджер, описание с расчётом), лот → confirmed со ссылкой; ниже — «нет/отклонена» (сервер блокирует). Менеджер видит только свои; руководство — все + фильтры + «Рейтинг менеджеров» (👑). **Действие лота** (звонок / КП (ватсап) / участие) — бейдж в строке, в раскрытой строке действие + комментарий и телефон клиента. Чек-лист лота удалён (09.08.2026).
- **Сделки:** канбан+список (в списке длинные названия — line-clamp 2 строки); **история этапов** (deal_stage_logs, хуки Deal): ⏱ на карточке канбана (сколько на текущем этапе) + «Тайминг этапов» во вкладке «История» (каждый шаг: когда вошла/ушла, сколько заняло, кто перевёл; уход в цех/отмена останавливает таймер); бэкфилл активным сделкам при миграции; фильтр-бар (поиск, менеджер, этап — скрывает остальные колонки, срок/договор с—по); карточка с вкладками (Задачи/Финансы/Документы/Комментарии/Доп.поля/История/Чат). «Название сделки» убрано — везде company_name (name зеркалит его). Поля: компания BAIA/ASU, клиент, адрес, № договора (колонка bin, 100 симв.), дата договора, источник-портал, товар (client_name), кол-во (lot_number)+ед.изм., сумма, срок, заметка.
- **Цех (Projects):** канбан секциями по цехам; у BAIA два цеха (project_stages.workshop / projects.workshop: «Металл цех», «Ағаш цех»), у ASU один (workshop=null). «Отправить в цех» при 2+ цехах — модалка выбора; «Далее»/степпер/«Готово» — в воронке своего цеха. **Доступ сотрудников по цехам** (users.workshops, JSON-список; форма сотрудника → «Доступ к цехам»): работник «Металл цеха» видит/двигает только свои заказы и секции (сервер отдаёт 403 и по прямой ссылке), можно выбрать оба цеха; пусто = все цеха (руководство, ASU, старые сотрудники); заказы без цеха видны всем. **Тайминг этапов** (project_stage_logs, хуки Project): бейдж «⏱ Nч Nм» на карточках (сколько заказ на текущем этапе) + блок «Тайминг этапов» на карточке заказа (история: каждый этап, когда вошёл/ушёл, сколько занял). Суммы от цеха скрыты.
- **ТВ-экраны (/screen, без логина, вход по 6-значному коду):** управление — Настройки → Экраны (коды по цехам + строка «Офис» на компанию, копирование кода, вкл/выкл, «Новый код» отключает старые — код сверяется на каждом показе; throttle 10/мин). **Экран цеха** — светлый канбан только своего цеха (без сумм, тайминг, часы, автообновление 10с); кнопки на карточке — «Далее →» двигает заказ на следующий этап, на последнем этапе («Отправка») — «Готово ✓ — в Логистику» с window.confirm: заказ завершается, сделка возвращается на Логистику (POST screen/projects/{id}/advance|complete по коду экрана в сессии, только заказы своего цеха/фирмы; complete — только с последнего этапа; единая логика ERP/экрана — ProjectService::completeAndReturnDeal). **Экран «Офис»** — сверху ВОРОНКА отдела крупными цифрами: Участвовал (лоты) → каждое ДЕЙСТВИЕ лота (Участие, Звонок, КП) → Выигранные, у каждой плитки факт/план (план лотов sales_plan_monthly, план выигранных sales_plan_won_monthly — оба на стр. Экраны); рейтинг менеджеров по ЛОТАМ (имя слева; справа персональная воронка-чипы, выиграл/лотов/сделок, ☎ лотов со звонком или КП) с автопрокруткой ТОЛЬКО этого блока (вниз-вверх при переполнении); лидер 👑 по выигранным; таблица «Лоты месяца» с действием по каждому; деньги не показываются; фильтр месяца; автообновление 10с; «план сделок/мес» (Setting `sales_plan_monthly`, ставит admin/financist на стр. Экраны) — справочный индикатор, на лидерство не влияет.
- **Склад:** свой у каждой компании; приход (admin/financist) с ценой закупки; таблица материал/ед/цена/поступление/сумма/списание (кликабельно — куда ушло)/остаток; материальный расход в сделке = кол-во × закупочная цена (авто, confirmed сразу, списывает остаток).
- **Финансы:** первым блоком **ДДС** — ручная Excel-сводка (dds_entries, БЕЗ связей с расчётами): счета компаний (банк/фактический остаток/дебиторский) + долги + дата, правят admin/financist, видит и director. **Счета**: сегодняшние сверху + прошлые аккордеоном (поиск по номеру), колонка «Сделка» (ссылка всегда, у удалённой — серым), статусы по-русски (Выставлен/Частично оплачен/Оплачен). «Аванс» (счета)+платежи, расходы сделок с ВИДАМИ — 🚚 доставка / 📦 закуп / прочие / материалы со склада (type в expenses; отдельные колонки в Сводном отчёте и разбивка на Аналитике) (pending → бухгалтер подтверждает с чеком и нал/банк) и расходы КОМПАНИИ по категориям (категории управляются «⚙ Категории»: добавить/переименовать/удалить, занятые — скрываются с сохранением сумм); Поступления денег (нал/банк, откуда) — сегодняшние + аккордеон прошлых с поиском/периодом; Расходы — так же (сегодня + прошлые аккордеоном); касса/банк = поступило − потрачено по способу оплаты (**касса — ЕДИНАЯ на холдинг**: наличные физически в одной кассе, расход налом любой фирмы уменьшает общий остаток; **банк — раздельно** по компаниям; **корректировка кассы** — ✎ на плитке, ТОЛЬКО админ: задаёт фактический остаток, разница хранится в Setting cash_correction и прибавляется к расчёту, история платежей/расходов и отчёты не искажаются, на плитке пометка «скорректировано»); дебиторка (авто по счетам + вручную); кредиторка СКРЫТА в UI по просьбе владельца 24.07.2026 (данные и бэкенд целы — вернуть: плитка + аккордеон payable в Finance/Index.vue); удаление любой финзаписи → уведомление СЕО и директору; «Доход» = итог Сводного отчёта (по сделкам: остаток − бонус; при фильтре месяца — сделки месяца по дате договора); селектор «Месяц» пересчитывает Доход/Оборот/Расходы/Итог за месяц (ЗП и налог — только «за всё время»; касса/банк всегда текущие). Расходы > 60% суммы договора → уведомление финансистам (однократно). **ДДС** (блок на Финансах): ручная Excel-сводка — счета компаний холдинга (банк/фактический остаток/дебиторский) + долги, с датой и итогами; НАМЕРЕННО без связей с расчётами системы (dds_entries); видят admin/director/financist, редактируют admin/financist.
- **Зарплата:** ведомость секциями **компания → отдел** со своими итогами по каждой фирме; сотрудник обеих фирм виден в обеих секциях, но его деньги входят в итог ТОЛЬКО основной фирмы (`primary_company_id` = наименьший company_id), в чужой секции строка приглушена с пометкой «учтено в ‹фирма›» — двойного счёта нет, сумма секций = плитке «К выплате». Видны ВСЕ активные сотрудники (оклад/аванс можно дать любому). К выплате = оклад + бонус − удержания + премии за месяц; корректировки (отгул/больничный днями = оклад/22×дни, штраф, аванс, премия) вводит financist/admin; **аванс** = реальные деньги: в форме выбирается нал/банк, автоматически создаётся подтверждённый расход компании (категория «Расходы по сотрудникам») — виден в Расходах на Финансах и уменьшает кассу/банк; удаление аванса удаляет и расход (payroll_adjustments.expense_id); бонус ступенчатый от маржи каждой won-сделки × доля фактической оплаты (min(1, paid/budget)).
- **Аналитика (руководство):** LIVE-режим (часы, автообновление 60с), SVG-диаграмма доход/расход по месяцам со шкалой и линией итога (hover-детали), донат по статусам, спидометр конверсии, воронка, топ менеджеров, ABC (пороги владельца: A ≤30% накопительно, B ≤50%, C — остальное), разбивка расходов сделок по видам (склад/доставка/закуп/прочие), цветные градиенты блоков, «требует внимания», «Деньги компании» (единая математика с Финансами через PayrollService/FinanceService). Вкладка **«По бухгалтерам»** (рядом с «По сотрудникам», в заголовке красный счётчик просроченных): сделки, застрявшие на этапах бухгалтера — АКТ и ЭСФ. Бухгалтер меряется по СВОИМ гейт-задачам (`StageTransitionService::createGateTask` ставит их роли `financist`), а не по владению сделкой: **ответственный по сделке остаётся менеджер** и показан в строке. **Просрочка — по сроку ЗАДАЧИ** (`tasks.due_date`, задаётся в «Настройки → Этапы» полем «срок в днях»), тот же срок, по которому бухгалтеру уже шлёт напоминания `tasks:notify-overdue`. На каждого: сколько на АКТ / на ЭСФ, сколько просрочено, сумма просроченных, максимальная просрочка в днях, и таблица сделок (номер, этап, менеджер, сумма, срок задачи, дней просрочки). Плитки сверху считают **уникальные** сделки: гейт-задача ставится КАЖДОМУ бухгалтеру, поэтому сумма по строкам заведомо больше числа сделок — в итогах двойного счёта нет. Вкладка «По сотрудникам»: рейтинг с местами (👑/🥈/🥉), шкала ЗП к лидеру, герой-шапка с градиентом, 6 цветных плиток показателей, колонки сделок Оплата/Акт/Просроченные.
- **Сводный отчет** (admin/director — целиком; **manager — свой срез**): МОП заходит на ту же страницу, но видит ТОЛЬКО свои сделки (`responsible_user_id` прибит к нему в контроллере — чужой `?manager=` в адресе не поможет), заголовок «Мой отчёт», блок «Мои показатели за период» вместо сводной по всем, фильтр менеджера скрыт. **Доход компании и маржа МОПу не показываются вообще** — вырезаны из props (плитка «Доход», колонки «Доход»/«Маржа» в сводке и таблице), он видит свой оборот, оплачено, расходы, налог, остаток и свой бонус. Плитки **«Сделки по этапам»** (обоим): сколько штук и на какую сумму висит на каждом этапе воронки, порядок — как в воронке, клик фильтрует таблицу по этапу. Сверху **«Сводная по МОП»** (сворачивается) — строка = менеджер: сделок / выиграл / **оборот** / оплачено / расходы / налог / бонус / доход / маржа + ИТОГО; клик по строке фильтрует таблицу по этому менеджеру; считается из тех же сделок, что и таблица, — итоги двух блоков сходятся по определению. Быстрый выбор **месяца** рядом с «с … по …» (раскрывается в границы месяца, фильтр — по дате договора, как «Месяц» на Финансах). Ниже — Excel-таблица всех сделок+цеха (закуп-склад / 🚚 доставка / 📦 закуп / прочие — раздельно, налог/остаток/маржа/бонус/доход); фильтр сотрудника: менеджеры сверху, остальные по отделам свёрнуты (ManagerPicker — тот же на стр. Сделки), зелёный градиент won+Акт/ЭСФ, жёлтый Логистика/Сборка; период фильтрует по дате договора (fallback — дата создания) — как «Месяц» на Финансах.
- **Чат:** мессенджер (группы, файлы, цитаты, правка, реакции, закреп, @упоминания, счётчики непрочитанных, архив); чат сделки привязан к deal_id. Фоновые вкладки сервер не поллят. **Группы по фирмам:** у группы company_id (BAIA/ASU/обе) — сотрудник видит только группы своей фирмы (админ — все), проверка и по прямой ссылке. **Корзина:** удаление группы и личного чата — мягкое (сообщения целы), admin/director возвращают или стирают навсегда (с файлами); канал сделки удаляется только со сделкой. **Участники:** вкладка «Участники» — добавить сотрудника в готовую группу (для группы фирмы — только её сотрудники) / убрать (✕). **Звук** нового сообщения (WebAudio, тумблер 🔔 в localStorage) + живые бейджи через лёгкий поллинг /chat/state (4с на переднем плане; в фоне — только state раз в 30с + браузерное уведомление Notification API, работает и на телефоне при открытой вкладке). **Кто прочитал:** ✓/✓✓ на своих сообщениях (по chat_reads), в группах — счётчик и имена по наведению.
- **Сотрудники (/users):** **компактный список** (строка на человека: аватар, имя со ⭐ руководителя и 🎂, контакты второй строкой приглушённо, роль, фирмы, действия по наведению; стаж — в подсказке на имени) секциями **компания → отдел** (BAIA / ASU, внутри — отделы фирмы); чипы фирм над чипами отделов; сотрудник обеих фирм показан в обеих секциях — в одноимённом отделе своей фирмы (по `departments.code`) живой поиск, фильтр-чипы отделов, мини-статистика, скрытие отключённых; экспорт CSV (Excel). У сотрудника: день рождения (🎂 бейдж ≤7 дн., ежедневная команда users:notify-birthdays 09:00 уведомляет руководство и главу отдела), дата приёма (стаж «в компании с …»). **Профиль /users/{id}** (руководство или сам): контакты, договор, сделки, заказы цеха, задачи, ЗП-расчёт+корректировки (деньги — admin/financist/director и сам). **Отделы:** руководитель (⭐ на карточке; получает уведомления о просроченных задачах своего отдела через tasks:notify-overdue).
- **Просроченные:** сделки (без ЭСФ/won; Акт — считается) + отдельно заказы цеха. **Задачи, Документы, Аудит (admin), Уведомления, Доп.поля, Настройки (Общие/Этапы/Экраны/Доп.поля), Переводы.**
- **Сотрудники (HR) + Отделы:** карточки по отделам (секции, живой поиск, фильтр-чипы, мини-статистика), у отделов руководитель (⭐ на карточке; получает уведомления о просроченных задачах сотрудников отдела и о днях рождения). Поля: день рождения (🎂 бейдж ≤7 дн., команда users:notify-birthdays ежедневно 09:00 уведомляет руководство), дата приёма (стаж), доступ к цехам (users.workshops), договор-файл. **Профиль /users/{id}** (руководство или сам): контакты, показатели, ЗП-расчёт+корректировки, сделки/заказы цеха/задачи. Экспорт CSV (BOM, «;»). Аванс сотруднику из корректировок ЗП автоматически создаёт confirmed-расход «Расходы по сотрудникам» (нал/банк) и удаляется вместе с ним.
- **Аудит (admin):** фильтры (раздел/действие/пользователь/период), всё по-русски (таблицы/поля/значения/даты/деньги), «не было»/«убрано» для пустых, ссылка на запись (#id → карточка), IP; фиксируются и корректировка кассы, и строки ДДС.
- Порядок меню: Аналитика → Просроченные → Сделки (перед ними Предв. сделки) → Цех → Склад → Сводный отчет → Финансы → Зарплата → Чат → … → Сотрудники → Профиль → Настройки.

## 4. Логика денег (единые формулы)
- **По сделке:** налог = бюджет × ставка (Setting tax_percent, 3%); остаток = бюджет − налог − confirmed-расходы; маржа % = (бюджет − расходы)/бюджет (ДО налога — по ней ступень бонуса); бонус = ставка(маржа) × остаток × min(1, оплачено/бюджет); **ручной % бонуса** по сделке (deals.bonus_rate_override, ставит financist/admin на карточке сделки, бейдж «вручную») перекрывает ступени ВО ВСЕХ расчётах (единый PayrollService::marginBonus).
- **Ступени бонуса:** ≤10%→0; 11–15→5%; 16–20→7%; 21–30→10%; 31–40→13%; ≥41→15% (PayrollService::bonusRateForMargin). **Ручной % по сделке:** финансист/админ может задать свой % бонуса конкретной сделке (deals.bonus_rate_override, карточка сделки → «Расчёт прибыли» → ✎; бейдж «вручную»/«авто», кнопка «Авто» возвращает ступени). Ручной % применяется ВЕЗДЕ единообразно: ЗП, Финансы, Аналитика, Сводный отчёт, экран «Офис» (PayrollService::marginBonus с override).
- **Доход компании** = фактические платежи по won-сделкам; **расход** — все confirmed сразу; «Доход (Сводный отчёт)» = Σ(остаток − бонус) по не-отменённым сделкам. Прибыль для компании по сделке = остаток − бонус. Один источник правды: PayrollService (companyTotals/perUser/dealBreakdown) + FinanceService (companyBalances/dealsIncome) — Финансы, Аналитика, ЗП, Сводный отчёт и экран «Офис» сходятся.

## 5. Ключевые бизнес-правила
- **Долг сотрудника** (`employee_debts` + `employee_debt_payments`, страница ЗП → раскрыть сотрудника → «Долг перед компанией»): бухгалтер выдаёт долг (сумма + фиксированный платёж в месяц + нал/банк) — как и аванс, автоматически создаётся подтверждённый расход компании и уменьшает кассу/банк. Дальше долг гасится САМ: команда `debts:charge` идёт по расписанию 1-го числа за прошлый месяц и удерживает `min(месячный платёж, бонус месяца, остаток)`. **Гасится ТОЛЬКО из бонуса — оклад не трогается никогда:** нет бонуса в месяце → удержания нет, остаток целиком переезжает дальше. Бонус месяца берётся `PayrollService::bonusByUserForMonth` (по дате договора — как «Месяц» на Финансах и в Сводном отчёте). Погашения хранятся помесячно с уникальным ключом (долг, месяц): команда идемпотентна, повторный прогон не спишет второй раз, догнать пропущенный месяц можно вручную `--month=YYYY-MM`. Ведомость показывает план текущего месяца («удержим − X, останется Y») и вычитает его из «К выплате». **Та же таблица долга и на карточке сотрудника** `/users/{id}` — с фильтром месяца в шапке блока «Зарплата»: месяц переключает и долг, и корректировки (раньше там висели последние 20 вперемешку, и профиль не сходился с ведомостью). Фильтр запоминается (`useStickyFilters`, ключ `user-card`). Долг закрывается сам при остатке 0; удаление долга убирает и его расход. **Аванс и долг — РАЗНЫЕ механики, обе через модалку** (просьба владельца 08.08.2026): **аванс** — разовая выдача, каждый месяц своя сумма, удерживается целиком в этом же месяце из ВСЕЙ выплаты (тип корректировки, «Корректировка ЗП» → «Аванс»); **долг** — переходящий остаток, фиксированный платёж в месяц и только из бонуса («+ выдать долг» у сотрудника). Оба создают подтверждённый расход компании. В обеих модалках стоит перекрёстная подсказка, чтобы бухгалтер не перепутал; в расчёте они независимы (аванс идёт в `deductions`, долг — в `debt_charge`) и не гасят друг друга.
- **Уведомление об удалении финзаписи ведёт к ХОЗЯИНУ записи:** самой записи уже нет, поэтому «Открыть» открывает сделку (расход/счёт/платёж по сделке) или заказ цеха; поступление и долг компании хозяина не имеют — там по-прежнему Финансы (`FinanceAudit::linkTo`, ссылка передаётся в `FinanceRecordDeleted`).
- **Удалять расходы может ТОЛЬКО бухгалтер/админ** (просьба владельца 08.08.2026) — любые, включая ещё не подтверждённые: у менеджера убрано право `expense.delete` в сидере, и это же продублировано ролевой проверкой в `ExpensePolicy::delete` (право можно вернуть через админку — правило должно держаться). Следствие: **материальное списание менеджер тоже больше не удаляет** — ошибся в количестве, просит бухгалтера удалить расход (остаток вернётся на склад) и заводит заново. Правку своего ещё не подтверждённого расхода менеджеру оставили: пока бухгалтер не подтвердил, это черновик.
- **Подтверждённый бухгалтером расход заморожен для автора:** как только бухгалтер подтвердил (чек + нал/банк, деньги ушли из кассы), менеджер не может ни удалить, ни изменить его — 403 с внятным текстом (ExpensePolicy::update/delete, кнопка удаления скрыта в FinancePanel). Правку закрыли вместе с удалением: иначе запрет обходится сменой суммы на 1 ₸. Признак заморозки — `confirmed_by`, а НЕ `status`: списание материала со склада система проводит сама (`status=confirmed`, `confirmed_by` пустой, бухгалтер его не видел) — там менеджер по-прежнему удаляет расход (остаток возвращается) и заводит заново, как учит форма. Удалять/править подтверждённый расход может только admin/financist (у директора прав на удаление финзаписей нет вовсе).
- **Выплаты сотрудникам связаны с человеком явно** (`expenses.employee_id` + `employee_payout` = advance|debt): раньше сотрудник жил только строкой в описании («Аванс сотруднику: Бахытжан»), а `responsible_user_id` у таких расходов значил «кому выдали», хотя у расхода по сделке — «кто потратил»: одна колонка с двумя смыслами, имя устаревало при переименовании, фильтровать выплаты по человеку было нельзя. Миграция 2026_08_15 разово восстановила связи из `payroll_adjustments.expense_id` и `employee_debts.expense_id` (не разбирая текст). В кассовой книге у такой операции — бейдж «Аванс»/«Долг» и ссылка на карточку сотрудника.
- **Касса (/cash-book)** — кассовая книга за день, как бумажный «Отчёт кассира»: остаток на начало → операции по времени → остаток на конец. Четыре плитки (начало дня, приход, расход, «Доступно сейчас» крупно), лента операций с тегами и **промежуточным балансом у каждой строки**, стрелки ←/→ по дням и кнопка «Сегодня». Источники — три потока наличных: оплаты по счетам налом, поступления в кассу, ПОДТВЕРЖДЁННЫЕ расходы налом; банк и pending-расходы в книгу не попадают. **Переключатель «Наличные / Банк»**: наличные единые на холдинг, банк раздельный по фирмам (книга банка сужается до текущей компании) — то же правило, что у плиток на Финансах. **Остаток на начало считается на лету** — всё движение до этого дня плюс ручная корректировка кассы (у неё нет даты, поэтому относится к прошлому); закрытия дня нет, новых таблиц не заводили. Видят admin/director/financist.
- **Зарплата — бонус за месяц + поиск:** плитка «Бонус за ‹месяц›» рядом с общим «за всё время» (`bonus_month` в строках и итогах, считается тем же `bonusByUserForMonth`, что и погашение долгов — второй раз не пересчитывается). **В «К выплате» месячный бонус НЕ участвует** — выплата по-прежнему от общего, это осознанное решение владельца. Над ведомостью — живой поиск по сотруднику и отборы «с бонусом за месяц / с долгом / с удержаниями»; суммы секций считаются по найденным (подпись «суммы секций — по найденным»), пустые секции скрываются, фильтр запоминается.
- **Предсделки — результат по действиям** (руководству, над таблицей): по каждому действию лотов → выиграно → конверсия % → сумма выигранных договоров; клик по плитке фильтрует список. Уважает фильтр месяца и менеджера, но не фильтр действия — иначе сравнивать не с чем. Плюс серверный фильтр `?action=` и селект «Все действия». В разбивке ЗП у сделки из лота — бейдж «◧ Участие/Звонок/КП»: видно, какое действие приносит бонус.
- **Предсделка: три ДЕЙСТВИЯ вместо чек-листа** (просьба владельца 09.08.2026). Действие — тип записи, выбирается при создании: **Участие** (умолчание) — полная форма с расчётом маржи; **Звонок** и **КП (ватсап)** — короткая: БИН, заказчик, товар, имя и телефон клиента, сумма договора + комментарий, без расчёта (лишние поля отбрасываются на сервере: тип записи — единственный источник правды). Комментарий есть у всех трёх. **Чек-лист предсделки удалён целиком** — модель, таблица `pre_deal_checklist_items`, колонка `checks`, маршруты и настройка пунктов; воронка ТВ-экрана «Офис» и счётчик у менеджера переведены с галочек на действия.
- **«Выиграл» больше не подтверждает расходы автоматом:** доставка/грузчики и сборка из лота переносятся в сделку в статусе `pending` — на маржу сделки и кассу не влияют, пока бухгалтер не подтвердит их чеком (раньше создавались сразу `confirmed`).
- **Карточка сделки, в самом конце — блок «Из предварительной сделки»:** действие, № лота, кто и когда внёс, срок тендера, расчётная маржа лота и его цифры (закуп/доставка/сборка/комиссия) как справка, плюс комментарий. Видно, что сделка выросла из лота.
- **Изоляция фирм в СПИСКАХ сотрудников** (`User::scopeOfCompany`, просьба владельца 15.08.2026): работающий только в ASU не показывается в BAIA — ни на странице «Сотрудники», ни в селектах ответственного по сделке/заказу, ни в фильтрах менеджеров (Сводный отчёт, Аналитика, Предсделки), ни в рейтинге ТВ-экрана «Офис», ни в списке клиентов и профиле. В режиме «Все компании» (админ/бухгалтер) видны обе фирмы. Сотрудник без единой фирмы виден везде — иначе новая карточка потеряется до того, как ей проставят фирму.
- **Отдел следует за фирмами сотрудника** (`UserController::realignDepartment`): при сохранении сотрудника, если его отдел принадлежит фирме, где он больше не работает, он переставляется на одноимённый отдел своей фирмы (по общему `code`); такого нет — отдел снимается. Без этого сотрудник оставался в отделе покинутой фирмы и считался по её норме часов.
- **Отделы принадлежат фирме** (`departments.company_id`): «Отдел продаж» BAIA и «Отдел продаж» ASU — РАЗНЫЕ отделы со своим руководителем ⭐ и своей нормой часов. `departments.code` — общий ключ одноимённых отделов разных фирм: по нему сотрудник, работающий в обеих, попадает в свой отдел в секции каждой фирмы. Списки/фильтры отделов сужены до текущей фирмы (`Department::forCompany`, в режиме «Все» — обе с колонкой «Компания»); в форме отдела фирма выбирается при создании (можно обе — заведётся копия в каждой) и НЕ меняется при правке. Миграция 2026_08_08 разово продублировала прежние общие отделы в обе фирмы.
- **Фильтры страниц запоминаются** (`useStickyFilters`, localStorage, свой ключ на страницу: users / deals / reports.deals / payroll / pre-deals / warehouse / analytics / finance). Явные параметры в адресе важнее запомненного фильтра — по прямой ссылке восстановление не срабатывает; «Сбросить» чистит и запомненное.
- **Две компании** BAIA/ASU: полная изоляция данных (worksInCompany в политиках, прямые ссылки тоже), свои воронки сделок и цехов (Настройки → Этапы: выбор компании и вида; у цеха — подвкладки по цехам, порядок 1..N внутри каждого). Режим «Все» (admin/financist) — сводно по обеим.
- **Спец-этапы по stage_type** (contract/design/shop_gate/logistics/assembly/act/esf/payment_won) — переименование не ломает логику; тип уникален в воронке.
- **Гейт-задачи этапов:** текст/роль/срок на этапе; при входе — задача каждому активному сотруднику роли + уведомление; сделка дальше не идёт, пока не закрыта. Галочку ставит роль гейта или admin. «Дизайн и расчет» → дизайнер (блокирует «Закуп»); «Закуп» → снабженец (отправку в цех не блокирует); АКТ/ЭСФ → бухгалтер.
- **Роли по этапам:** менеджер до Акта; АКТ/ЭСФ/Оплата — только financist/admin; после Акта менеджеру read-only. Оплата успешно НЕ требует полной оплаты (остаток — в дебиторку). Удаление сделок — только admin (+bulk); каскад: заказ цеха отменяется, ссылки помечаются «сделка удалена».
- **Нумерация сделок:** BAIA-001/ASU-001 по компании; считаются только ЖИВЫЕ (при удалении номер освобождается: `…#del{id}`); удалили все — снова с 001; миграция 2026_07_21 разово перенумеровала живые с 001 (чаты по deal_id — история цела).
- Счёт с суммой 0 запрещён; статусы счетов — только пересчётом платежей; расход/счёт не переставить на чужую сделку.
- Просрочка: ЭСФ/won исключены, Акт — просрочен; и сделки, и заказы цеха.

## 6. Скорость и безопасность
- **Перф:** OPcache на проде (Plesk → PHP Settings) — обязателен; после каждого деплоя `php artisan optimize`; индексы под горячие запросы (add_performance_indexes + add_money_hot_path_indexes: morph-связки expenses/invoices, status+payment_method, chat_messages); чат/экраны не поллят из фоновых вкладок; статика с `Cache-Control: immutable, 1y` (public/.htaccess, имена версионированы); brotli на сервере; код-сплит по страницам.
- **Безопасность:** SecureHeaders (nosniff, X-Frame-Options, Referrer-Policy, Permissions-Policy, HSTS), принудительный HTTPS в production, троттлинг логина и публичных форм, скрытые файлы в public/ не отдаются (403), прод `.env`: APP_DEBUG=false, SESSION_SECURE_COOKIE=true. Аудит-лог, уведомления об удалении финзаписей. Рекомендовано владельцу: регулярные бэкапы БД в Plesk, ротация FTP-пароля после любых передач.

## 7. Запуск и деплой
```
php artisan serve            # http://localhost:8000
npm run dev                  # или npm run build
php artisan schedule:work    # уведомления о просрочке
php artisan test             # перед каждым push
```
Первый вход — учётка администратора из сидера (`DatabaseSeeder`), пароль сменить сразу. Прод: Plesk Git Pull → `migrate --force` (Laravel Toolkit/веб-скрипт — системный CLI PHP без pdo_mysql) → `php artisan optimize`. Подробности — `DEPLOY.md`. Никакие реальные доступы в репозиторий не попадают.
